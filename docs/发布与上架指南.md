# 发布指南：把 dsh-pocket-relay 做成独立项目并上架 dsh-market

> 这份文档描述**从当前这个改造后的工作副本**出发，一路做到「GitHub 上有自己的仓库 + dsh-market 里能搜到并一键安装」的完整流程。
>
> 读之前先记住三条会颠覆直觉的事实：
>
> 1. **dsh-market 不是投稿入口。** 它是市场客户端，插件目录来自精选列表 [`awesome-dsh-plugin`](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin)。上架 = 往**那个仓库**提 PR，市场与目录站会自动收录（通常 1 天内生效）。
> 2. **npm 上架不是必需，但强烈建议。** 市场安装的优先级是「npm 包 → 作者提供的 GitHub Release 预构建 tarball → 整仓源码下载」。只挂 GitHub 源码的插件，用户装它要拉整个仓库 + 本地跑构建脚本，慢且容易失败。
> 3. **改名的成本主要在「身份」而不是「代码」。** 你这个副本的 `package.json` 仍自称 `dsh-pocket`、README 和 badge 都指向 `shaobeichen/dsh-pocket`。不改干净，市场里的卡片会把你导流回上游仓库，用户装到的也是上游版本。

## 0. 先做一次决策：叫什么、放哪、什么协议

这三件事定了再动代码，否则后面全要返工。

| 决策 | 说明 | 建议 |
| --- | --- | --- |
| **npm 包名** | 全小写、kebab-case；未被占用即可。可带 scope（如 `@kinderao/dsh-pocket-relay`） | 用不带 scope 的 `dsh-pocket-relay`，卡片更好看；被占用再退到 scope |
| **显示名** | 市场卡片标题，可读性优先 | `DSH Pocket Remote` |
| **GitHub 仓库** | 必须是 `https://github.com/<owner>/<repo>` 形态——`url` 字段不是这个形态会被列表直接拒收 | `kinderao/dsh-pocket-relay` |
| **license** | 你的副本是 GPL-2.0（继承上游）。**改了就得保留**，不能顺手换成 MIT，否则是侵权 | 保持 `GPL-2.0`，并在 README 里注明基于上游二次开发 |
| **版本号** | 从 `2.10.6` 继续还是归零？建议**语义化 + 明确区分**：自研版本从 `1.0.0` 起，并在 README 写清「基于 dsh-pocket 2.10.6 改造」 | `1.0.0` |

> ⚠️ 归属与合规：你这是上游项目的衍生作品。README 里明确写「Forked from shaobeichen/dsh-pocket，GPL-2.0」是**必须**的，既合规也避免社区误认你是原作者。上游 README 若含作者个人推广、二维码、赞助链接，发布前应替换或删除。

## 2. 发布前的自检（别跳过）

用户在市场上点「安装」之前，看不到你的终端。这些错误一旦带上架，修一次要走一遍 PR 流程。

```powershell
# 1) 全量测试：期望 257 个用例，254 通过；3 个失败是既有环境问题
#    （download.test.js 需要联网下 cloudflared、2 个 tunnel-args 在 Windows 上跑无扩展名脚本）

# 2) Go 服务端
cd relay; gofmt -l .; go vet ./...; go test ./...; cd ..

# 3) 客户端 bundle 必须与源码同步（改了 client/*.jsx 或 locales 就要重新构建并一起提交）
node client/build.mjs
git status --porcelain client/client.js   # 应该没有输出，否则说明 bundle 忘了提交

# 4) 预构建服务端二进制（下面 §3.2 的 Release 要用）
npm run build:relay:all
```

**验收清单：**

- [ ] `npm test` 没有**新增**失败
- [ ] `client/client.js` 已随源码重建并提交
- [ ] `relay/dist/` 下三个平台的二进制都在（要作为 Release 资产上传，**不**提交进仓库、**也**不该进 npm 包）
- [ ] `npm pack --dry-run` 里没有 `relay/dist/`，包体积在 1MB 量级而非十几 MB（见 §3.2）
- [ ] 插件在干净 profile 里能加载（见 §2.1）

## 3. 上架 dsh-market（三步）

### 3.1 第一步：让 `package.json` 满足市场契约

市场对插件的**硬性**要求其实很少，但它读的字段决定了卡片长什么样、安装走哪条路、以及会不会显示「与当前宿主不兼容」。

```jsonc
{
  "name": "dsh-pocket-relay",
  "version": "1.0.0",
  "description": "把 DSH 装进口袋：局域网 / 自建中继远程访问，设备级认证，多台电脑共存与热备。 · Remote access for DSH over LAN or your own relay, with per-device auth and multi-PC failover.",

  "license": "GPL-2.0",
  "repository": { "type": "git", "url": "git+https://github.com/kinderao/dsh-pocket-relay.git" },
  "homepage": "https://github.com/kinderao/dsh-pocket-relay",
  "bugs": { "url": "https://github.com/kinderao/dsh-pocket-relay/issues" },

  "engines": { "node": ">=22" },

  // ↓ 宿主兼容性：市场用它判断「这个插件在当前 DSH 上能不能装」
  //   可选但强烈建议——不声明会一直显示成「未知」，用户不敢装
  "peerDependencies": {
    "@deepseek-ai/cordis": "^4.0.1"
  },

  // ↓ 插件身份：market 靠这个认识你是一个 DSH 插件
  "dsh": {
    "bundle": { "patch": "./cordis.patch.yml" },
    "client": {
      "inject": [
        "@deepseek-ai/dsh-client-connection",
        "@deepseek-ai/dsh-client-ui-slots",
        "@deepseek-ai/dsh-client-ui-layout",
        "@deepseek-ai/dsh-client-locale",
        "@deepseek-ai/dsh-session-log-export"
      ],
      "platform": "web"
    }
  },

  // ↓ 发布白名单：漏掉运行所需文件 = 用户装完报模块找不到；
  //   但**别把 relay/dist 的服务端二进制打进去**（体积问题见 §3.2）
  "files": ["bin", "lib", "client", "cordis.patch.yml", "README.md", "LICENSE"]
}
```

**关于 `engines.dsh`：** 市场也支持用 `engines.dsh` 声明所需 DSH 版本区间，并配合同版本线的 `@deepseek-ai/dsh-*` peer 一起判定。两个声明是**合取**关系（都必须满足）。如果你不确定 DSH 的版本策略，就先只声明 `@deepseek-ai/cordis` 这一个 peer——**宁可不声明，也别写错区间**：写窄了会把能用的用户挡在门外（市场在确认不兼容时会直接拒绝安装并提示「这个新版本要求更新的 DSH」）。

**`cordis.patch.yml` 必须存在**：市场安装后靠它把插件挂进 profile。你的仓库已有这个文件，当前内容是：

```yaml
- insert:
    - id: dsh-pocket
      name: dsh-pocket
```

改名时要注意：市场的「热禁用 / 启用」开关是往 profile 补丁里写 `- id: <这里这个 id>` + `disabled: true|false`，**它认的是这个 `id`，不是 npm 包名**。所以

- `id` 应当与你在 profile 里希望的 loader 条目名一致；`name` 必须与 **npm 包名**一致（loader 按 `name` 去解析包）。
- 如果你把包名改成 `dsh-pocket-relay`，这里的 `name` 就要跟着改，`id` 可保留 `dsh-pocket`（老用户的停用开关才不会失配），也可以一并改掉——但**改了之后老用户的启用/停用状态会失效**，自己权衡。

### 3.2 第二步：让安装走「快车道」（预构建 Release + 给 npm 瘦身）

市场安装的优先级：

| 顺序 | 方式 | 用户体感 |
| --- | --- | --- |
| 1 | **npm 包** | 数秒，无需构建 |
| 2 | **作者提供的 GitHub Release 预构建 tarball** | 数秒，无需构建 |
| 3 | 整仓 GitHub 源码下载 | 慢；若仓库带 `pnpm-lock.yaml` 还可能因 registry 不匹配而构建失败 |

#### 先说一个必须处理的体积问题

`package.json` 的 `files` 里有 `"relay"`，于是 `npm pack` 会把**整个 relay 目录**打进去。实测当前 tarball：

```
files count = 56
size        = 17.4 MB（压缩后）
unpacked    = 43.5 MB
```

其中 `relay/dist/` 的四个二进制就占了约 31MB，外加 Go 源码。**但这些文件插件运行时根本不需要**——`lib/` 与 `bin/` 里没有任何一处引用 `relay/dist`：Go 中继是给用户**部署到自己服务器上**用的，不是插件安装时要跑的东西。

把 31MB 服务端二进制塞进每个「手机访问」用户都要下载的 npm 包里，代价是：下载更慢、registry 存储膨胀、用户装一个手机远程插件却拖下一堆 Linux/Windows 服务端程序（也容易让人困惑）。

**建议：把服务端二进制从 npm 包里摘出去，改为放在 GitHub Release 资产里**，用户按 `relay/README.md` 自行下载部署。改法：

```jsonc
// package.json
"files": [
  "bin",
  "lib",
  "client",
  "cordis.patch.yml",
  "README.md",
  "LICENSE"
]
```

如果希望 npm 包里仍带上服务端**源码**与文档（体积极小，便于用户自行编译），可以单独收窄成：

```jsonc
"files": [
  "bin", "lib", "client", "cordis.patch.yml", "README.md", "LICENSE",
  "relay/main.go", "relay/go.mod", "relay/go.sum",
  "relay/internal", "relay/config.example.json", "relay/PROTOCOL.md",
  "relay/README.md"
]
```

**但无论哪种，`relay/dist` 都不该进 npm 包**。改完用这条命令确认：

```powershell
npm pack --dry-run --json |
  ForEach-Object { ($_ | ConvertFrom-Json)[0] } |
  Select-Object size, unpackedSize, @{n='files';e={$_.files.Count}}
```

#### 再把二进制挂到 Release 资产

你的 Go 服务端二进制有 ~10MB×3 个平台，**绝对不要**让用户现场编译（他们机器上多半没有 Go）。所以要把二进制作为 Release 资产挂上去。

**好消息：本仓库已经有现成的两条流水线**，不要从零新建：

| 文件 | 触发 | 作用 |
| --- | --- | --- |
| `.github/workflows/test.yml` | push 到 `main` / PR | `npm ci && npm test` |
| `.github/workflows/release.yml` | **手动**（Actions → Release → Run workflow） | `npm test` → `npm run release`（semantic-release：按提交自动定版本，写 CHANGELOG、发 npm、建 GitHub Release） |

⚠️ **不要用 `git tag` 手动发版**：semantic-release 会自己打 tag 并写 `package.json`。你手动打的 tag 会让它算错版本来源（它靠「上一个 tag 以来」的提交决定下一个版本号），两边打架。

你需要做的是**在现有 release 流程里补一个 job：构建 Go 二进制并挂到 Release 资产上**。

**接法 A（推荐）：给 release 流程加一个依赖它的构建 job**

```yaml
# 追加到 .github/workflows/release.yml 的 jobs: 下面
  relay-binaries:
    # 等 semantic-release 发布完再构建，版本号才拿得到
    needs: release
    runs-on: ubuntu-latest
    permissions:
      contents: write
    steps:
      - uses: actions/checkout@v4
        with:
          ref: main          # 取 semantic-release 刚提交的版本号
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - uses: actions/setup-go@v5
        with: { go-version: '1.25' }

      # 用 semantic-release 刚写进 package.json 的版本号，
      # 保证二进制内嵌版本与 Release tag 一致
      - id: v
        run: echo "version=$(node -p "require('./package.json').version")" >> "$GITHUB_OUTPUT"

      # 关键：显式传版本号。build.mjs 的默认值是硬编码的，
      # 忘了传就会产出一个版本号对不上的二进制（我们改造时真踩过一次：
      # 管理端显示的版本从 0.2.0 变回了 0.1.0）
      - run: DSHP_RELAY_VERSION="${{ steps.v.outputs.version }}" npm run build:relay:all

      - run: cd relay/dist && sha256sum * > SHA256SUMS.txt && cat SHA256SUMS.txt

      - uses: softprops/action-gh-release@v2
        with:
          tag_name: v${{ steps.v.outputs.version }}
          files: |
            relay/dist/dsh-pocket-relay-linux-amd64
            relay/dist/dsh-pocket-relay-linux-arm64
            relay/dist/dsh-pocket-relay-windows-amd64.exe
            relay/dist/SHA256SUMS.txt
```

**接法 B：把二进制发版拆成独立的手动 workflow**，与 npm 发版解耦，版本号手填。适合你想「插件发小版本、服务端二进制只在真的改了 Go 代码时才重发」的节奏。

发版动作本身：

```
GitHub → Actions → Release → Run workflow
```

（提交信息请遵循 Conventional Commits，`feat:`/`fix:` 决定版本号是 minor 还是 patch。当前这批改造建议用 `feat:`。）

> `relay/dist/` 已在 `.gitignore` 第 7 行忽略，这是**对的**——二进制只作为 Release 资产上传，不进 git 历史。别为了「方便」提交它，否则仓库体积每次发版涨 30MB。同时按上面的建议把它从 npm 的 `files` 里也摘掉。

### 3.3 第三步：准备好卡片的门面（截图与描述）

市场卡片会展示描述与截图，这直接影响点击率：

- **描述**：`plugins.json` 里的 `description` 是 `{ "zh": "...", "en": "..." }` 结构，**中英各写一份**，跟随界面语言切换。一句话说清「这是什么 + 解决什么痛点」，别写成功能清单。
- **截图**：两种来源。
  1. 在目录条目里**作者策展**（`screenshots: [...]`），卡片直接显示，零额外请求——推荐。
  2. 不策展时，市场会在用户打开安装弹窗时**自动从你的 README 抽取**。
- **图片必须走 GitHub 图床**：市场只允许从 GitHub 自己的图片域加载，其它域名的 URL 会在创建 `<img>` **之前**就被丢弃。所以 README 里的截图请用 `https://raw.githubusercontent.com/...` 或 `user-images.githubusercontent.com`，不要用自己的图床或对象存储。
- **文件名里有这些词的图片会被当品牌图排除**：`badge/shield/logo/icon/avatar/sponsor/qr/wechat/npm/coverage/license/status` 等。你的 `docs/` 里有二维码和 banner 类图片，**注意别把它们当成功能截图**；真正该展示的是「设置页中继配置」「设备管理」「管理端电脑表格」这类界面图。

### 3.4 发布到 npm（本仓库已自动化）

`package.json` 里已有 `publishConfig`（`access: public` + 官方 registry），且 release workflow 内置了 `@semantic-release/npm`，所以**正常路径不需要手动 `npm publish`**：配好 `NPM_TOKEN` secret，跑一次 Release workflow 即可。

如果你确实要手动发（例如 CI 挂了临时救急）：

```powershell
npm login                    # 本机当前未登录（npm whoami 报 ENEEDAUTH）
npm pack                     # 先检查内容，别把 test/ docs/ relay/dist/ 发上去
npm publish --access public
```

⚠️ 手动发版要和 CI 的版本号错开：semantic-release 依赖「上一个 tag 以来的提交」算下一个版本，你手动 `npm version` 出的号会让它的推断错位。

发布后回到目录条目，把 npm 包名填进 `npm` 字段——**这一步能让安装从「下载整仓」变成「数秒装好」**。

> 关于 `description` 的两种形态，别搞混：
> - `package.json` 里是**一个字符串**（npm 规范只允许字符串）。
> - 目录条目 `plugins.json` 里是**按语言分的对象** `{ "zh": ..., "en": ... }`。
>
> 所以 §3.1 示例里用一个字符串同时写中英（用 `·` 分隔）是给 npm 看的权宜写法；目录条目请按 §3.5 拆成两个字段。

### 3.5 提交目录条目（上架的关键一步）

去 [`awesome-dsh-plugin`](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin) 仓库提 PR，在列表里**加一条**。市场与目录站会自动收录，通常一天内生效。

条目字段（来自市场读取的 `plugins.json` 结构）：

```jsonc
{
  "name": "dsh-pocket-relay",          // 显示名/身份，与 npm 包名一致最好
  "owner": "kinderao",                    // GitHub owner
  "url": "https://github.com/kinderao/dsh-pocket-relay",  // ⚠️ 必须是纯 https://github.com/owner/repo
  "category": "remote",                  // 一个或多个分类 id
  "description": {
    "zh": "把 DSH 装进口袋：局域网或自建中继远程访问，设备级认证，多台电脑共存与热备。",
    "en": "Remote access for DSH over LAN or your own relay, with per-device auth and multi-PC failover."
  },
  "npm": "dsh-pocket-relay",            // 有 npm 包就填，能大幅加速安装；没有填 null
  "tarball": null,                       // 或指向你的 Release 预构建 tarball
  "install": "dsh plugin --profile web add dsh-pocket-relay",
  "added": "2026-09-13",                 // 收录日期
  "screenshots": [                       // 可选：策展截图，必须 GitHub 图床
    "https://raw.githubusercontent.com/kinderao/dsh-pocket-relay/main/docs/pocket-settings-zh.png"
  ]
}
```

**提交时的常见退件原因：**

| 问题 | 后果 |
| --- | --- |
| `url` 不是 `https://github.com/owner/repo`（带 `.git`、带路径、用别的域名） | **直接拒收**——列表脚本会校验这个字段的形态 |
| `description` 缺 `zh` 或 `en` | 界面切到另一种语言时卡片空白 |
| `category` 为空或不是已知分类 | 条目会被市场丢弃（解析层要求至少一个可用分类） |
| 截图用了非 GitHub 图床 | 卡片静默不显示图 |
| `name`/`url` 与仓库实际的 `package.json` 对不上 | 用户点了安装但装不上，或装成了别的包 |

**再次强调：不要往 [`dsh-market`](https://github.com/dsh-market/dsh-market) 仓库提插件条目**——那个仓库是市场应用本身，不是插件目录，提了也会被要求转去 `awesome-dsh-plugin`。

## 4. 发布后：更新怎么走

用户装了之后，市场会**逐个插件检测更新**：npm 包对比 registry 上的版本，GitHub 来源对比锁定 commit 与 HEAD。所以：

- **走 npm 路线**：直接在 Actions 里跑一次 Release workflow。semantic-release 会自动升版本、写 CHANGELOG、发 npm、建 Release；你补的那个 job 再把二进制挂上去。用户在市场点「更新」即可。
- **只推代码没发版**：用户不会看到更新（npm 上版本没变，GitHub 上 HEAD 变了——不同来源行为不同，所以**别依赖这个**，要发就正式发一次版本）。
- 版本号请严格遵循语义化：市场会用你 `package.json` 的 `version` 与 `engines.dsh` 一起判断要不要拦下这次更新。

你也可以在自己的设置页里调用市场的[更新 API v1](https://github.com/dsh-market/dsh-market/blob/main/UPDATE-API-V1.md)（beta）做插件内更新，无需复制包管理逻辑。你的插件已经有「常开中继 + 管理端」这类需要版本感知的能力，后续可以考虑用它做「服务端与插件版本不匹配」的提示。

```powershell
# ③ 自检

node client/build.mjs && npm run build:relay:all

# ④ 换 remote 并推送
git remote set-url origin https://github.com/kinderao/dsh-pocket-relay.git
git remote add upstream https://github.com/shaobeichen/dsh-pocket.git   # 可选
git push -u origin main

# ⑤ 发版：先在 GitHub 上加 NPM_TOKEN secret，再
#    Actions → Release → Run workflow（semantic-release 自动定版本、发 npm、建 Release）
#    并给 release 补的 relay-binaries job 会自动把三个平台二进制挂到 Release 资产
#    ⚠️ 不要手动 git tag —— 会和 semantic-release 打架

# ⑥ 去 awesome-dsh-plugin 提 PR，加一条目录条目（url 必须是纯 github.com/owner/repo）
```

**完成判据：** 在 dsh-market 里搜到你的插件 → 点安装 → 数秒装好 → 刷新页面即可用（无需重启）→ 卡片显示的是**你的**仓库与描述，而不是上游。

> 关于「npm 发布」这一步：本仓库的 release workflow 已经内置 `@semantic-release/npm`，只要配好 `NPM_TOKEN` secret，走 Release workflow 就会自动发 npm。所以在 §3.4 里**不需要**手动 `npm publish`——手动发布只在你不想用 CI 时才需要，注意别和 CI 的版本号撞车。
